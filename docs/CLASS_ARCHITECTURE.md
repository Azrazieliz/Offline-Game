# Class Architecture

This document records the current authoritative class-system design. Classes are representative, system-recognized mastery states rather than restrictive RPG job slots.

## 1. Core model

- A Class is earned from actual learned skills, practice, mastery and demonstrated capability.
- Classes are recognized automatically; the player does not select a class first in order to become capable of its discipline.
- The protagonist begins classless.
- Multiple Classes can coexist simultaneously.
- There is no universal primary/secondary equipped-class slot limit.
- Classes are non-restrictive. A Swordmaster may still use a bow, firearm, magic, tools or another discipline.
- Off-discipline performance is determined by actual proficiency, talent, Factors, anatomy, equipment and skills rather than an arbitrary wrong-class penalty.
- Pugilist is a valid example of a Class that may emerge from sufficiently developed unarmed capability.

## 2. Normal, specific/composite and Grand Classes

- The framework has at least two recognition tiers: **Normal Class** and **Grand Class**.
- Normal Classes identify coherent developed disciplines.
- When multiple disciplines, skills or Factors become one integrated style, the system may recognize a **specific/composite Class** with its own authored name.
- Parent mastery remains part of the character; recognizing a composite Class does not delete the earlier disciplines.
- A **Grand Class** represents exceptional mastery, scope, coherence and demonstrated capability beyond ordinary Class standards.
- Grand recognition is descriptive of what the character has become. It does not suddenly grant a generic bundle of unrelated powers.
- Grand status can apply to a conventional discipline or to a unique/composite Class.

## 3. Skills cause Classes, not the reverse

- Skills, techniques, experience and mastery produce Class recognition.
- A Class does not automatically inject a package of new skills.
- A character may learn techniques before any corresponding Class is recognized.
- Learned skills remain unless an explicit mechanic removes/seals/damages the capability.
- Class advancement therefore comes mainly from actual use, training, relevant achievements and development of underlying capability rather than generic class XP.

## 4. Evolution, fusion and Factors

- Classes may branch/evolve when the underlying skill set develops into a new coherent specialization.
- Multiple Classes may fuse into a specific/composite Class when the combination becomes a real integrated discipline.
- Factors may alter, mutate or enable unusual Class evolutions when they materially change the body/existence.
- Universal Classes should generally not use species Factors as arbitrary gates.
- If a style fundamentally requires unique anatomy/existence, treat it as a character-/Factor-specific Class or unique specialization instead.
- Character-/Factor-specific Classes can coexist with ordinary Classes and can themselves become composite or Grand.

## 5. Gameplay representation

- Classes can be referenced by AI, training, story logic, appraisal, social recognition, authored synergies and eligibility checks.
- They do not replace the actual underlying capability checks.
- Raw stats should come from actual training, Factors, Rank, equipment and mechanics rather than arbitrary bonuses caused solely by a Class label.
- The UI should surface the most relevant/highest-developed Classes and Grand Classes rather than an unwieldy equipped-class list.
- No universal class-count cap is required; relevance sorting handles readability.
